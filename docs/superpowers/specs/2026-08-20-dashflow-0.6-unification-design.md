# DashFlow 0.6 Product Unification Design

## Status

Approved direction from the product owner on 2026-08-20. This specification defines the implementation boundary for DashFlow 0.6.0.

## Product Decision

DashFlow is the only product that will continue to be maintained and released. The separate `obsidian-dashboard` repository remains available as historical reference, but it is not part of the DashFlow build, runtime, or data contract.

Old `obsidian-dashboard` Vault data will not be migrated or parsed. DashFlow 0.6 keeps one canonical Markdown/frontmatter model:

- Tasks are Markdown checkbox lines with DashFlow-compatible scheduling markers.
- Projects and habits are notes identified by their configured `type` frontmatter value.
- Dashboard layouts, widget configuration, UI preferences, caches, and derived state live in the DashFlow plugin `data.json`.

DashFlow's own existing `data.json` remains supported and must be upgraded safely.

## Goals

1. Make every registered Widget usable in the normal Work surface.
2. Restore secure AI credential storage without breaking v0.5.5 or v0.5.6 users.
3. Protect user content and UI configuration from accidental deletion, reset, and corrupt-data overwrite.
4. Reduce first-run complexity and present a coherent product vocabulary.
5. Remove automatic third-party image requests while preserving DashFlow's photographic Hero direction.
6. Ship the result as a reproducible, documented DashFlow 0.6.0 release.

## Non-Goals

- Do not parse, import, convert, or delete old `obsidian-dashboard` Vault data.
- Do not delete the `obsidian-dashboard` source repository.
- Do not introduce a second database or proprietary task store.
- Do not redesign the application from scratch or replace the existing TypeScript/DOM architecture.
- Do not add new productivity domains beyond the features already registered in DashFlow.

## Product Information Architecture

The top-level product vocabulary becomes:

- **Today / 今日**: personal summary, current priorities, habits, recent notes, and reading highlight.
- **Work / 工作台**: the active user-configured Dashboard. It displays every Widget in that Dashboard whose `hidden` property is not `true`.
- **Inbox / 收集箱**: unprocessed task captures from the configured Inbox file.
- **Projects / 项目**: focused project view.
- **Calendar / 日历**: focused time view.
- **Habits / 习惯**: focused habit view.
- **Review / 复盘**: focused weekly review view.

User-created Dashboard definitions are presets within Work, not a competing navigation hierarchy. The default Dashboard name becomes `默认工作台`. Existing custom Dashboard names are preserved.

Creation vocabulary becomes:

- **快速记录** opens Quick Add and writes to Inbox or Daily Note according to the configured capture target.
- **灵感看板** refers only to the opportunity-board workflow stored in its configured Markdown file.
- **新建任务 / 新建项目 / 新建习惯** remain structured creation commands.

## Widget Visibility Architecture

`DashboardRenderer` remains responsible for rendering registered Widget instances. `ProductExperienceService` may create synthetic Today and Inbox pages and may provide purpose-specific layouts for Projects, Calendar, Habits, and Review.

Work must not use a hard-coded Widget allowlist. In Work:

1. Iterate over Widget instances in the active Dashboard.
2. Display every instance where `hidden !== true`.
3. Apply that instance's saved desktop layout.
4. Preserve the existing mobile ordering and collapsed state behavior.

Focused sections may continue to select relevant core Widget types. A regression test must compare all registered Widget types against normal Work visibility so a newly registered type cannot silently disappear.

## Credential Security And Upgrade

AI and WeRead credentials use Obsidian `SecretStorage` through `SecretComponent`. `data.json` stores only a secret identifier.

Upgrade logic distinguishes existing states without exposing a secret in logs:

1. If `aiSecretId` names an existing SecretStorage entry, keep it unchanged. This is the v0.5.5 path.
2. If `aiSecretId` contains a v0.5.6 plaintext key, store it under a stable DashFlow SecretStorage identifier, replace `aiSecretId` with that identifier, and persist the sanitized settings.
3. If neither condition is valid, leave the integration unconfigured and show a clear settings message.
4. Never transmit the stored identifier as an API bearer token.

The upgrade must be idempotent and tested for v0.5.5 identifiers, v0.5.6 plaintext keys, empty values, local endpoints, and repeated startup.

## Safe Plugin Data Loading

Schema migration becomes an explicit pipeline instead of assigning the current schema version unconditionally.

- Parse and validate loaded plugin data before mutating or saving it.
- Keep unknown future top-level data intact where safe.
- Create a recoverable backup snapshot before the first write performed by a schema upgrade.
- If Dashboard data is malformed, do not overwrite it automatically. Start with an in-memory recovery Dashboard and show a recovery notice with export/reset actions.
- Only persist a reset after explicit user confirmation.
- Record the completed schema version after all migration steps succeed.

The backup may live inside plugin data as one bounded `recoveryBackup` snapshot. Keep only the most recent pre-upgrade snapshot to avoid unbounded growth.

## Destructive Actions

Use one consistent interaction policy:

- Deleting a Dashboard or custom template requires the existing timed second click.
- Removing a Widget and resetting a layout require a timed second click because they remove UI configuration.
- Deleting an opportunity item uses an immediate soft-delete interaction with an Obsidian Notice offering Undo. The write is committed, but the removed item is retained in memory until the undo window expires.
- No destructive action should rely on color alone; the confirmation label must change.

Vault task, project, and habit content is never removed by layout actions.

## First-Run Experience

On the first successful load with no prior DashFlow data, show a compact setup modal before opening the full product surface. It must:

1. Explain that Markdown remains the source of truth.
2. Report detected counts for notes, checkbox tasks, projects, and habits after the initial index is ready.
3. Offer three starting layouts: Minimal, Daily Focus, and Project Management.
4. Confirm Inbox, project folder, and habit folder defaults.
5. Create the selected Dashboard and mark onboarding complete.

The modal is skippable and can be reopened from Settings. It does not create sample business notes automatically.

Existing users must not see onboarding after upgrade.

## Offline Hero Assets

Alpine, Paper, and Midnight retain distinct photographic scenes, but all default scenes are bundled with the plugin. They must not request Unsplash or any other third-party host.

- Generate three coordinated wide bitmap assets without text, logos, people, or watermarks.
- Optimize them for an Obsidian Hero crop and package them under `assets/heroes/`.
- Resolve them through the plugin resource path rather than remote CSS URLs.
- Keep local user-selected Vault images as the highest-priority override.
- The Obsidian theme remains a no-photo option.

Release packaging and source packaging must both include the assets.

## Release And Documentation

Release version becomes `0.6.0` in `package.json`, `manifest.json`, `versions.json`, source constants, CI artifact names, and release workflow references.

Add or update:

- Current architecture documentation reflecting the index/query/service/widget/product layers.
- README quick start, canonical Markdown formats, first-run behavior, network/privacy disclosures, credential storage, backup behavior, and upgrade notes.
- A changelog entry explaining the Widget visibility and credential fixes.
- A lockfile for reproducible `npm ci` builds; CI must use `npm ci`.
- License metadata only if it can reuse the repository owner's existing license text without changing ownership or license terms. Otherwise document the unresolved release requirement rather than inventing a license.

## Testing Strategy

Follow test-driven development for each behavior change.

Required automated coverage:

- All registered Widget types remain visible in Work unless the instance is explicitly hidden.
- Focused sections still filter and lay out their intended core Widgets.
- AI SecretStorage upgrade matrix and idempotency.
- Malformed plugin data does not trigger an automatic destructive save.
- Recovery backup creation and explicit reset behavior.
- Timed confirmation for Widget removal and layout reset.
- Opportunity delete and Undo restore the exact item and order.
- Onboarding appears only for true first run, selects the requested template, and can be reopened.
- No source or compiled CSS contains third-party Hero URLs.
- Release metadata is consistent and packaged assets exist.

Run the full Node test suite, TypeScript no-emit validation, production build, `node --check main.js`, and a clean-worktree check after generated artifacts are accounted for.

Because this is an Obsidian plugin, add a small fake-App integration harness for data loading and SecretStorage behavior instead of relying only on source-text assertions. Visual verification must cover the Hero, Work with extension Widgets, first-run modal, destructive confirmation states, and mobile layout in a test Vault when an Obsidian runtime is available.

## Rollout Order

1. Fix Work Widget visibility and add the regression matrix.
2. Restore SecretStorage and implement credential upgrade.
3. Add safe plugin-data migration and recovery behavior.
4. Standardize destructive actions.
5. Implement terminology and first-run onboarding.
6. Add bundled Hero assets and remove remote defaults.
7. Align versioning, packaging, documentation, and reproducible builds.
8. Run complete automated and runtime verification.

## Acceptance Criteria

- A user can add and use every registered Widget outside layout editing.
- Upgrading from v0.5.5 or v0.5.6 does not expose, misinterpret, or lose an AI credential.
- Corrupt Dashboard configuration is never overwritten without explicit approval.
- Every destructive UI action has confirmation or Undo.
- New users reach a useful Work surface through a short, optional setup flow.
- Product terminology has one meaning per concept.
- Opening DashFlow with default settings makes no third-party image request.
- DashFlow 0.6.0 builds reproducibly and its documentation matches runtime behavior.
