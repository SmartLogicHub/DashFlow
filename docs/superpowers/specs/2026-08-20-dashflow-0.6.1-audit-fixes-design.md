# DashFlow 0.6.1 Audit Fixes Design

## Scope and decision

The approved 0.6.1 patch corrects three release-blocking findings from the post-0.6.0 audit. It does not change the Markdown data model, UI layout, onboarding choices, or licensing policy.

## Safe schema-8 settings loading

Schema-8 plugin data currently validates only that `settings` is an object, then casts it to `DashFlowSettings`. A corrupted primitive can consequently reach a runtime consumer such as `homeHeroImagePath.trim()`.

The migration boundary will validate every known setting against the primitive type of its default. Missing keys receive their default and are safely persisted. A present key with an incompatible primitive type enters the existing non-destructive recovery path: DashFlow uses fallback data in memory, retains a redacted backup, and does not overwrite the original data automatically.

## Onboarding close lifecycle

Completion and dismissal are distinct outcomes. Completion saves the selected setup, marks onboarding complete, releases the modal lock, refreshes views, and opens the dashboard. Dismissal (Escape, close button, or programmatic close) only releases the modal-open lock; it deliberately leaves onboarding pending so automatic or manual reopening remains possible.

## Installable release package

The release workflow will build a `DashFlow-v<version>.zip` whose root contains the standard Obsidian plugin files and whose `assets/heroes/` directory retains its required hierarchy. Standalone runtime files remain release assets for existing installation flows. CI source archives will include the lockfile and changelog. The README will direct manual installation through the ZIP to avoid flattening Hero assets.

## Validation

Regression tests will cover corrupted schema-8 values, the dismissal lifecycle wiring, version metadata, and ZIP packaging. The patch must pass the complete Node suite, TypeScript check, production build, bundle syntax check, artifact-layout inspection, and whitespace/git-state checks.
